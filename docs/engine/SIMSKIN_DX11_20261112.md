# Installed SimSkin / CAS shader investigation

This is a source-linked implementation record, not a claim that the editor
already reproduces the complete game renderer. Installed game version observed:
**1.129.39.1030**. No game process was contacted. Original game/creator assets,
DXBC and disassembly stay in ignored `.local/`; none belongs in a release.

## Exact source boundary

The selected installed `Shaders_DX11.precomp` SHA256 is
`62ffab0f85c3af8ace5a375c968216d1ada2b1c9c2d18f32aa4b25d250a0b101`.
The DATA root resolves to payload version 6 at 656. It has 77,771 outer records,
7,947 VS records and 30,009 PS records. Field-relative pointers and 1-based stage
references match the maintained primary
[PRECOMP format research](https://github.com/Demeterio/TS4-Animation-Browser/blob/38598aaf4142b93d46bc452fde088e962cad3372/modding-resources/precomp/guides/FORMAT_REFERENCE.md).
That research's older build is structural guidance, not automatic qualification
of this installation. The selected current streams independently decompress as
Raw Snappy, have the recorded compact lengths, form bounded DXBC containers and
are accepted by Microsoft's `D3DDisassemble` without loading the game.

Actual GEOM shader hashes identify authored material families. The PRECOMP also
contains separate source-named **SimSkinCAS** (`DF0863B8`) and **simglassCAS**
(`D13E993D`) families, in addition to **SimSkin** (`548394B9`) and **SimGlass**
(`5EDA9CDE`). Names are not guessed: their lowercase FNV1 hashes match the
installed named records. Static inspection of the retained, non-executable
client analysis section now identifies the actual CAS override producer at
RVA`1A0FB20`: SimSkin→SimSkinCAS, SimGlass→simglassCAS and corresponding
ghost/wings pairs. The same producer binds CPUSkintone from its context and
CASAmbientIntensityTexture through a dedicated native getter. The mapping is
implemented as an explicit-context functional seam, not an automatic guess.
The full caller context and permutation selector are still unqualified.
Choosing the first matching shader is insufficient.

The earlier adjacent-data observation was deliberately unqualified. Its first
located consumer at`1A0FFE0` actually builds ghost remaps, not the normal CAS
override. Only the subsequent independently identified`1A0FB20` producer
establishes the CAS mapping. Original client bytes remain unchanged; neither
the private analysis section nor proprietary disassembly is distributed.

## Source-declared feature fields

The installed named shader-set metadata retains mode pairs, a feature-selection
program and named variant fields. Its serialized structure agrees with the
preserved first-party EA2014 `ShaderSet`/`VariantField` template; each current
field name independently reproduces its stored lowercase FNV1 hash. The
[sanitized current field record](evidence/source-shader-variant-fields.json)
retains the observed multiplier, start and range. No program bytecode is shipped.

SimSkinCAS declares`MAP_NORMAL=0x80`, `MAP_SPECULAR=0x100`, `MAP_CUBE=0x200`,
`MAP_EMISSION=0x400`, `MAP_SHEEN=0x800`, `OPT_SKINNING=0x10`,
`OPT_MEDATORLIGHTING=0x40`, `OPT_CPU_SKINTONE=0x1000`, `OPT_PET=0x2000`,
`OPT_ENABLE_FUR=0x8000` and`OPT_ENABLE_SKIN_SPECULAR=0x200000`, each with range 2
and start 0. Shadow-map type occupies multiplier 4/range 4. Fade, morph channels,
paint-pelt/eraser, wing paint, iridescence and skin emission have separate fields.
Therefore candidate3049's mask`0x80` is positively identified as the source's
normal-map variant, rather than named from the visible operation alone.

The named SimSkinCAS feature program has 221 words and references actual parameter
names such as NormalMap, SpecularMap, CPUSkintone, Medatorlighting, PaintPeltMode
and EnableSkinSpecular. Its [actual interpreter](SOURCE_FEATURE_VM_20261112.md)
now matches1,384 controlled original-instruction results in native Rust.
Caller-provided renderer/material input producers remain a separate gate.
Field definitions alone do not prove
the complete live feature vector. The world and glass families have different
field assignments: a bit value cannot be reused across families by assumption.

The separate source CPU-skintone flag explains the real one-plane PS3144 path.
It does not prove that the reference-tool atlas equals the game's CPU-composited
texture. Both native CPU and GPU construction routes require their actual
source rules; neither licenses a generic baked approximation as complete CAS.

## Actual sampled resources and register contracts

Binding names are recovered independently from the stage resource binding
records, global parameter index/hash table and installed name pool. The same
names hash back to their stored identifiers; this is stronger than guessing
from the image's visible contents.

PS3038 has five texture/sampler pairs, in slot order:

- `t0/s0`: `OverlayTexture`, hash`4DC0C8BC`, main UV.
- `t1/s1`: `SkinToneAndMakeupTexture`, hash`5E2CC5B9`, main UV.
- `t2/s2`: `ClothWithAlphaTexture`, hash`69EDEC9E`, main UV.
- `t3/s3`: `SkinDetailHSL`, hash`3C410F96`, sampled at
  `(OverlayTexture.GREEN,0)`, **not** the main UV.
- `t4/s4`: `CASAmbientIntensityTexture`, hash`E02DF0F4`, the second source UV set.

PS3038's single CB0 is 176 bytes. `LightDirections[4]` starts at0,
`LightColors[4]` at64, `SkinDetail2ndOverlayOpacity` at128,
`CASRimFalloff` at144 and `CASAmbientIntensity` at160. Each of the last three
occupies a 16-byte register. Source defaults for these lighting values are zero;
the engine must supply context/tuning values. Zero defaults are not a valid
replacement lighting profile.

PS3038's input semantic contract is `TEXCOORD0.xyz` world normal,
`TEXCOORD1.xy` main UV, `TEXCOORD2.xy` second UV and `TEXCOORD3.xyz`
camera-minus-world-position. `COLOR0` is declared but unused. Register numbers
are not semantic indices.

PS3049 adds `t4/s4=NormalMap` (`6E56548A`) and shifts ambient to`t5/s5`.
Its CB0 is 192 bytes: directions0, colors64, `NormalMapScale`128,
second-overlay opacity144, rim falloff160, ambient intensity176.
It adds `TEXCOORD6.xy` normal UV and `TEXCOORD7.xyzw` transformed tangent/hand.
VS919 computes normal UV as mainUV times `NormalMapUVxform.zw` minus
`NormalMapUVxform.xy`. Source UV1 remains independent for ambient sampling.

## Recoverable composition, in order

The following arithmetic acts on shader sample values. Actual SRV UNORM/sRGB
views, sampler address/filter state, render-target space and later compositing
must be qualified separately. There is no explicit gamma conversion in this
baseline instruction sequence. Encoded-source RGB must not be declared linear
merely because the arithmetic has been recovered.

Let `d=OverlayTexture.g`, `H=SkinDetailHSL(d, 0).rgb`,
`S=SkinToneAndMakeupTexture.rgb`, `K=ClothWithAlphaTexture` and
`w=SkinDetail2ndOverlayOpacity.x`. For each component:

```text
adjusted = S + (S*H-S)*0.5
overlay(b,d) = b<0.5 ? 2*b*d : 1-2*(1-b)*(1-d)
first = overlay(adjusted,d)
second = overlay(first,d)
skin = first + (second-first)*w
albedo = skin + (K.rgb-skin)*K.a
```

These CAS candidates apply **no diffuse multiplier**. Overlay RGB is not
ordinary colored clothing; its green channel is a detail/lookup control in
this path. Clothing alpha is used inside the native composite, not passed
through as final framebuffer alpha. A single baked SimRipper atlas cannot
represent the complete input contract.

World PS17731 has a separate delta after its diffuse multiplication:
`albedo=lerp(albedo,CASDyedTexture.rgb,CASDyedTexture.a)`. This texture is NOT
bound by any of the 1,569 unique nonzero PS references observed in the separate
CAS family. It must not be invented as the CAS color-editing implementation.
CAS color changes still require the real composite-construction and edit-state
path. Other CAS permutations have different contracts: for example PS3144
uses OverlayTexture RGB and a diffuse value directly, without these skin planes.

## Normal convention and basis

The selected CAS normal-enabled path and independently examined world paths
agree on the following:

```text
q = sampleNormal.(alpha,blue) * floatBits(40008102)
                              + floatBits(BF850A14)
z = sqrt(max(0,1-dot(q,q)))       # before normal scale
q = q * NormalMapScale.x
N = normalize(interpolatedNormal)
B = cross(N,interpolatedTangent.xyz) * interpolatedTangent.w
result = normalize(q.x*T - q.y*B + z*N)
```

The two constants are exactly the float32 values of `255/127` and`-132/127`.
For an unfiltered UNORM texel this centers encoded alpha/blue at byte 132.
This is neither a generic RGB normal nor an assumed alpha/green DXT5nm normal.
Do not change the blue/alpha planes during DDS decoding.

VS919 (CAS) and VS2929 (world) explicitly emit tangent handedness`-1`.
Their input tangent W is unused. Their packed vertex decode also remaps XYZ
with exact scale/bias constants before transforming it. GEOM float tangents,
engine GPU packing, deformation of tangents and this VS contract are separate
steps; supplying a generic tangent W without selecting the matching vertex
path does not establish correct game deformation.

Five actual installed body normals now decode in native Rust. Their complete
mip-stream restoration is byte-identical to the original pinned GPL s4pi
`DSTResource.Unshuffle` method compiled unchanged in a minimal harness. Native
BC3 RGBA is pixel-identical to independent Pillow for all 3,801,088 first-mip
pixels. `image`'s DXT rounding differed by one level, so DST5 deliberately uses
the already qualified native BC3 convention. This proves decoding, not GPU
filtering or the complete shading result.

## Source normal addressing defaults

The installed material builder1A2E540 initializes an identity transform, then
uses explicit GEOM `NormalMapTransformOverride` (hash `5844E532`, original
literal at `022CBD50`) when declared. This is distinct from the later shader
binding named `NormalMapUVxform`. If the GEOM override is
absent, it invokes selector1A2C150 with the render context's species word and
two codes from its38-byte mesh record at+1C/+20. The first is actual CASP
BodyType: named native `_cas.get_caspart_bodytype` independently returns the
same native field at+64. The second is v27+ SharedUVSpace/UVoverride, with raw
zero replaced by BodyType in native CASP reader19FA470. Writer1A290D0 establishes
the record-field chain; the pinned GPL reader independently matches its source
field placement. Native assets now retain that exact raw u32 separately from
the early u8 TextureSpace. The source routine sometimes leaves the initialized value
untouched, so the Rust helper returns `None` for that operation rather than
inventing an extra fallback.

The native
`material::shader::normal_uv_default_for_source_context` reproduces its exact
conditional vector selection.7,168 controlled inputs match the isolated
original machine routine bit for bit, including untouched outputs. That
emulation executes82,062 instructions at51 distinct addresses with no intercepted
calls, I/O or game contact. The actual source shader uses
`normalUV=mainUV*xform.zw-xform.xy`; those offsets are not interchangeable with
subtracting before scaling. The
[sanitized record](evidence/normal-uv-defaults.json) retains exact float bits and
qualification limits. Actual material presence, explicit-value precedence and
the selected shader/vertex convention remain caller obligations.

## Actual CAS lighting equations

Normalize `N` and camera-to-surface view vector`V`. Let
`h=saturate(N.x+0.5)`, `falloff=lerp(CASRimFalloff.y,CASRimFalloff.x,h)` and
`rimColor=lerp(LightColors[3].rgb,LightColors[2].rgb,h)`. Sample the ambient
texture at source UV1 and compute:

```text
rim = pow(1-saturate(dot(N,V)),falloff)*rimColor*ambientTexel.g
ambient = lerp(CASAmbientIntensity.x,CASAmbientIntensity.y,ambientTexel.a)
key0 = saturate(dot(N,LightDirections[0].xyz))*LightColors[0].rgb
key1 = saturate(dot(N,LightDirections[1].xyz))*LightColors[1].rgb
rgb = albedo*(rim+ambient+key0+key1)
outputAlpha = 0
```

This directly explains the source tuning's two keys, two rim endpoints and
ambient range. LightDirections are shader inputs; camera-relative/orientation
construction from room tuning remains a separate caller obligation. No
authored fill light, inverse-square attenuation or guessed ambient polynomial
belongs in this CAS path. Output alpha zero must be interpreted together with
the native render-pass/blend contract rather than used as material opacity.

## Implemented seam and next qualification

[Native CPU references](../../native/material/src/shader.rs) preserve the
specific candidate boundaries. [JSON reference executable](../../native/material/examples/shader_reference.rs)
exposes albedo, normal, lighting and final RGB independently for comparison
against original installed bytecode. No asset or game process is accessed by
that executable. The original-bytecode offscreen comparison lives privately
and is being broadened to adversarial channels, UVs, keys/rims and normal scale.

The next fidelity root causes, in dependency order, are native layer-stack
construction for each bound plane; native UV0/UV1/normal/specular addressing;
CAS family/feature/quality selection; matching vertex packing and tangent
deformation; sampler/SRV formats; complete render-pass states; then specular,
sheen, reflection/translucency and final color output. Drawing the right GEOM
with the wrong combined texture is not an accepted full-Sim result.

## Original installed shader execution route

Original DXBC can be created by a Rust-owned D3D11 renderer through
[CreatePixelShader](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11device-createpixelshader).
The offscreen checks demonstrate this actual asset boundary. Shipping need not
redistribute any shader bytecode: resolve and pin the selected installation.
This technical boundary is not a new grant of rights to proprietary binaries.

[D3D11On12](https://learn.microsoft.com/en-us/windows/win32/direct3d12/direct3d-11-on-12)
can use the existing D3D12 device and queue, with an offscreen
[wrapped resource](https://learn.microsoft.com/en-us/windows/win32/api/d3d11on12/nf-d3d11on12-id3d11on12device-createwrappedresource),
acquire/release, explicit input/output states and immediate-context flush.
The cached wgpu30.0.1 DX12 HAL has`raw_device`, `raw_queue`,
`texture_from_raw`; wgpu's`create_texture_from_hal` requires matching actual
driver resource state. This is a feasible integration seam, not a completed or
performance-qualified backend. A CPU-readback/upload production bridge would
add avoidable latency and must not be called an optimized renderer.

Keeping the original shaders removes a substantial equation-porting risk;
porting the verified equations to WGSL retains the existing GPU ownership
model. Neither route supplies missing native texture stacks, constants,
permutation selection, pass states or postprocessing. Choose using independent
image comparisons and actual frame/latency measurements once those inputs are
qualified, without an unrelated framework migration.
